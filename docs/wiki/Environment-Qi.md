# 环境真元交换契约

状态：**Protobuf 数据定义、有界编解码和消息内约束校验已实现；[环境配置](Environment-Configuration.md)另提供 TOML、chunk 区域及浓度/传播计算。** 环境库存、并发额度分配、吸收执行和交换事务尚未接入；当前 `InMemoryBodyStore` 仍只把死亡释放与加工损耗记入单一环境账户。这里定义后续聚灵和宿主环境接入共用的边界。

## 职责与入口

框架负责描述供给、交换及成功回执。宿主根据身体所在世界和位置选择来源，管理区域库存、浓度、扩散、共享供给预算和原子提交。Fabric 单机由内置服务端提供这些事实，Bong 或其他语言宿主使用同一契约。交换消息不绑定坐标格式或某种生物的吸收器官；Java 环境参考规则使用可配置的 chunk 分区。

协议源是 `shared/src/main/proto/kizuna/meridian/v1/environment.proto`；两端由 protoc 生成 `EnvironmentMessages`，与其他协议一起进入 JAR、描述集和协议 ZIP。Java 校验入口是 `EnvironmentProtobuf.encodeOffer/decodeOffer`、`encodeExchange/decodeExchange`、`encodeReceipt/decodeReceipt`，另外提供对应的 `validateOffer/validateExchange/validateReceipt`。交换原始 Protobuf 字节，沿用[协议规模与存在性限制](Protocol-and-Security.md)。

这些都是**经过认证的宿主与权威身体实现之间的内部事实**，不属于 `RequestEnvelope`，不能注册为客户端上传入口。消息携带 ID 不构成授权；即使客户端也能生成消息，宿主仍须验证生产方和来源选择。`parseFrom` 只解析格式，`EnvironmentProtobuf` 只校验事实关系，都不会执行转账。

## 三种消息

| 消息 | 字段 | 含义 |
|---|---|---|
| `EnvironmentQiOffer` | `protocol_version` | 当前为 1，与身体 schema 2 和账户 revision 独立 |
| 供给 | `source_id`、`source_revision` | 宿主内跨世界唯一、永久不复用的来源身份，以及非负权威版本 |
| 供给 | `body_id` | 该份供给适用的身体，不能挪给另一具身体 |
| 供给 | `available_qi` | 当前版本允许本次吸收的逐相态、逐属性上限，单位元；可为空 |
| 供给 | `max_absorption_per_second` | 对该身体所有种类合计的吸收上限，元/模拟秒；0 表示仅可释放 |
| 供给 | `valid_from`、`valid_until` | 同一时钟域和世代下的半开有效区间 `[from, until)`，必须有正时长 |
| `EnvironmentQiExchange` | `exchange_id`、`offer` | 权威端生成的稳定交换 ID，以及计算实际采用的完整供给事实 |
| 交换 | `expected_body_revision` | 计算前的身体版本，提交时必须仍匹配 |
| 交换 | `started_at`、`ended_at` | 本次稳定结算区间 `[start, end)`；纯释放可为同一时刻 |
| 交换 | `absorbed_qi`、`released_qi` | 两个方向分别记录的毛额，空方向也显式提供空账户 |
| `EnvironmentQiReceipt` | `exchange` | 已提交的原始交换，保持供给和明细以支持去重与恢复 |
| 回执 | `body_revision`、`source_revision` | 提交后版本，分别为候选中的旧版本加 1 |

供给只是一份带版本的事实，**不预扣资源、不产生新库存，也不预留余额**。它可以只披露实际库存的一部分，不能把 `available_qi` 当作完整区域存档。来源身份、版本和供给策略由宿主管理；位置映射不需要写进通用身体结构。

`optional` 数值在业务上必填，合法的 0 也须显式提供。真元复用 `QiInventory`：允许混相、混属性与第三方属性，同种类只能一行，明细数量为正，空账户用空列表。所有连续数值及总量必须有限，版本使用非负 `int64`。

## 区间与吸收校验

供给窗口和交换的四个时间游标必须同域、同世代。必须满足：

```text
valid_from <= started_at < valid_until
started_at <= ended_at <= valid_until
吸收各类数量 <= available_qi 中的同类额度
吸收总量 <= max_absorption_per_second × (ended_at - started_at) / 1000
```

时间差先按整数毫秒计算，再转换为模拟秒；生物老化倍率不影响吸收速度。吸收必须有正时长，零速率或零时长不能吸收正数真元。纯释放可在有效窗口内瞬时发生，不消耗吸收带宽，也不要求环境已有库存。右端点可以作为区间的结束，不能作为零时长释放的起点；宿主须为该新时刻提供有效供给事实。

数量和速率上限严格比较，不允许供给透支。逐类扣除还检查浮点数能否实际体现这笔扣款，速率与时长乘积溢出时拒绝；宿主可以缩短结算区间。不能通过先抵消释放来通过吸收校验：吸入 2 元并释放 1 元，需要的吸收额度仍然是 2 元。至少一个方向必须有转移，双空交换不能产生成功回执。

一次交换只绑定一个身体和一个来源。来源选择、身体所在位置或供给条件改变时，先结算旧稳定区间，再取得新供给；不能用最终位置的浓度倒推整个离线区间。跨来源的连续运行拆成顺序交换，每次沿用前次提交后的身体版本。

## 宿主提交必须满足的行为

以下是接入方必须实现的事务语义，当前编解码器不会查询世界或执行这些步骤：

1. 认证生产方并校验身体访问权。在事务内按 `body_id + exchange_id` 查回执：同键同已解码内容返回原回执；同键不同内容拒绝。不要按 Protobuf 原始字节是否相同判断重试。已成功请求先返回旧结果，不因当前版本或供给过期而重新执行。
2. 隔离身体、来源账户及相关共享供给预算，核对两个预期版本。宿主验证来源确实对应本次身体位置、供给事实没有被伪造，且所用条件在整个区间成立。实时提交检查有效性；离线推演只能使用宿主保存或重建的可信历史区间，不能无限延用已失效的旧供给。
3. 校验身体确实能吸收或释放这些明细。吸收区间必须属于身体本次尚未结算的有效活动时间，不能通过换交换 ID 或获取新供给再次使用已消费的时间。`LIFESPAN_ONLY` 冻结吸收；死亡只清账释放。具体摄入器官、局部容量和开拓规则由身体算子验证。
4. 先按相态和属性从**真实环境库存**扣除 `absorbed_qi`，再加入 `released_qi`。供给额度不能代替真实库存，也不能用同笔释放补足超额吸收。宿主还须检查多个身体在重叠区间内的共享供给额度，已用额度随状态一起保存；换来源 revision 不会重新获得同一时间的带宽。
5. 将新身体、新环境库存、供给预算和成功回执一起原子提交。身体和来源版本分别增加 1；任一版本已到 `Long.MAX_VALUE` 则拒绝。任一步失败全部回滚，不在提交后的审计通知中执行转账。

环境库存、扩散或其他消费者改变供给依据时，宿主更新来源版本，使旧候选重新校验或重算。**来源版本只能防止使用旧事实，不能单独证明带宽没有被重复消费**，因此共享预算和身体已结算时间也属于事务检查。跨进程实现仍须提供同等原子性，Protobuf 本身不提供分布式事务。

幂等键由可信身体身份约束，交换 ID 在该身体生命周期内不复用。回执与两个账户状态一起保存、一起恢复；不得仅靠重放回执恢复已入账资源。没有另行定义过期重试规则前，不清理去重记录。一个交换对应一次身体提交；宿主若将交换并入同次身体命令，两类回执描述同一个身体 revision，不再额外增加一次。

## 守恒与转换

```text
环境新账 = 环境旧账 - absorbed_qi + released_qi   （逐相态、逐属性）
身体新总元 = 身体旧总元 + absorbed_qi.total - released_qi.total
```

`absorbed_qi` 表示从环境取走的原始种类。器官转换后的种类写入身体实际账户，转换损耗作为 `released_qi` 退回环境；损耗仍是真元，不能从总账消失。宿主应按对应身体算子的结果核对明细和总量，不能仅凭上面总量相等就允许伪造属性转换。

释放不自动改变相态和属性。死亡释放保持原种类，当前器官加工损耗按无属性游离态返回；环境内退化和扩散由后续世界实现处理。回执只记录本次越过身体边界的数量，供给事实和回执都不加入身体总元。

既有 `TimeAdvanceResult.released_qi` 与这里的释放明细在接入同一时间结算时必须表示同一笔释放，不能各发放一次。旧内存适配尚未采用本契约；后续接入时需要将原来的单环境入账路径统一到来源事务，再加入吸收。

## 当前验证与下一步

整体契约回归覆盖供给固定字节、零值存在性、混相/自定义属性往返、双向毛额、瞬时释放、非法供给、跨时钟与区间、超库存/错种类/超速、浮点极限、版本递增和客户端入口拒绝。两端产物校验确保协议及描述集同步分发。

下一步为宿主来源查询与交换事务接入，再实现首脉聚灵。多人竞争、回滚、重试去重、分段推进一致性和保存恢复需要在执行层补充整体验收，不能把当前消息校验视为这些行为已经实现。
