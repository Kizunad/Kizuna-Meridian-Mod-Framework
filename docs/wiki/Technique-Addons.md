# 功法附属 JAR

状态：已实现[附属包注册与缺包诊断](Addon-Integration.md)、`OrganRecipeCatalog`、类型化器官配方及执行意图、组织能力查询与做功。功法知识、学习、蓝图、增益和世界动作仍待实现；0.x API 尚未冻结。下方候选表不是可编译示例。

经脉基础模组提供身体规则，附属包提供具体功法。官方基础功法也放在独立附属包，不能让核心反向依赖官方内容。

功法内容包与可选 3D 经脉世界 Addon 职责独立：配方和路线模板引用身体模块及端口能力，不要求存在特定 3D 设施或显示坐标；基础操作面板和 3D 铺带均可调用已学内容。交互设计见[经脉操作与 3D Addon](Inner-World.md)。

## 已实现的器官配方接口

附属 JAR 通过 `AddonBundle.organ_recipes` 提供 protoc 生成的 `BodyMessages.OrganRecipe`。宿主收集完整包集合，经 `AddonRegistry.load` 检查归属、依赖、宿主能力和类型引用后取得 `registry.recipes()`，作为 `BodyCommandHandler` 第六个参数。五参数构造器安装空目录，基础功能可独立运行。

独立配方编解码仍可使用 `CapabilityProtobuf.encodeRecipe/decodeRecipe`；直接构造 `OrganRecipeCatalog(List<BodyMessages.OrganRecipe>)` 是底层入口，只检查配方及重复 `id + version`，不替代包级依赖校验。

| 配方字段 | 规则 |
|---|---|
| `id` / `version` | 命名空间 ID 与正整数版本，运行时精确引用 |
| `organ_kind` | 与实际器官类型匹配，不按器官名称或人体位置判断 |
| `input` / `output` | 固定剂量 `QiInventory`；输入非空，输出总量不得大于输入，可为空 |
| `duration_millis` | 正数模拟毫秒；当前为内容固定加工时长，与端口搬运吞吐独立 |
| `minimum_realm` | 启动所需最低境界；具体属性及相态的阶段限制由宿主安装的内容定义 |

调用方提交 `body_command.start_organ_recipe { organ_id, recipe_id, recipe_version }`，不能上传配方本身或产物剂量。宿主必须检查是否已学会及其他世界条件；目录中的“已安装”不等于角色“已解锁”。原有授权、私有策略、可信时间、revision 和去重路径同样适用。

一次加工按以下规则执行：

1. 检查器官和所属部位仍有 HP、无其他加工、类型/境界符合、缓存中每种原料足够。
2. 原子扣除缓存输入，创建一个 `OrganProcess`。该记录持有固定配方事实，输入成为加工中账户；预计输出不计入总账。一个器官最多一个任务。
3. `advance_time` 到达完成时刻，移除加工账户，把产物加入器官缓存；`输入总量 - 输出总量` 以无属性游离态进入环境账，与身体及回执原子提交。
4. 到期器官或所属部位 HP 为零时阻塞，全部原料保留；恢复后显式结算可在同毫秒完成。不自动重试、循环生产或自动启动下一批。

器官空间由缓存和加工中原料共同占用，入向在途再预约剩余空间。已发起加工保存完整定义，因此卸载包或注册新版本不会改变这笔任务；卸载后未发起的新请求返回 `RECIPE_NOT_FOUND`。暂停仅寿命模式会冻结加工剩余时间。死亡前完成的任务先产出并释放损耗；同毫秒死亡优先，直接释放尚未转换的输入。没有取消、部分加工、热重载或状态改造命令。

这版支持属性/相态真元转换，**不内置默认转换效率或人体器官配方**。数值测试配方不代表平衡结论。原材料、灵食、气粒子等外部资源输入仍需宿主事务能力，不能用空输入配方制造免费真元。

## 已实现的组织能力

`Anatomy.TissueDefinition.capacity` 保存三个独立基础值：`strengthNewtons`（N）、`burstWatts`（W）、`enduranceJoules`（J）。肌肉、皮肤、骨骼仍使用内容类型 ID；被动组织可声明全零。经脉容量和通路状态不改写这些值，改造后的实际构型可以提供不同基础能力。

`get_tissue_capability { body_id, tissue_id }` 返回带身体 revision 的 `TissueCapability.available`，与完整身体查询共用读取权限。当前参考公式为：

```text
完好比例 = min(组织 HP / 组织最大 HP, 所属部位 HP / 部位最大 HP, 1)
疲劳余量比例 = max(0, 1 - 当前疲劳 / 疲劳容量)
可用力量、功率、做功预算 = 各基础值 × 完好比例 × 疲劳余量比例
```

死体或寿元已耗尽的身体返回零能力。`exert_tissue { tissue_id, force_newtons, power_watts, duration_seconds }` 按当前上限验证力量、功率和 `功率 × 秒数` 的做功预算，再按消耗预算的比例增加该组织疲劳；成功只增加一次 revision。全部负载参数必须为正，数值溢出或精度吞掉做功/疲劳变化时拒绝。请求是宿主授权的单次做功事实，时长用于计算能耗，**不会推进时间或创建持续动作**；负载按动作开始的能力检查。

能力查询不扣资源，做功不直接生成攻击伤害或移动。真实世界动作与这次扣疲劳的对应、限频、知识及装备检查由宿主负责。恢复、训练成长、持续静态支撑、真元增益、武器招式和作用于指定组织的 5 秒 buff 尚未实现；后续复用同一组织身份与权威状态。

## 后续扩展面

| 候选契约 | 用途 | 边界 |
|---|---|---|
| 功法知识与学习来源定义 | 将已安装配方、模板与实际学习事件关联 | 复用已实现的 `AddonRegistry` 内容目录，宿主验证解锁事实 |
| `TechniqueDefinition` / `OrganRecipeDefinition` | 声明目标能力、输入属性/相态、剂量、时间、精力、条件和作用 | 只组合已提供的类型化操作，参数有单位和范围 |
| `TechniqueBlueprint` | 定义经脉供给路线及执行入口 | 映射到实际身体，不能虚构端口或就绪储量 |
| `BodyQuery` / `BodyCommandGateway` | 查询允许的只读状态，提交受校验操作 | 不能直接写 HP、寿命、真元或私有存档 |
| `TechniquePresentation` | 图标、说明、动画、粒子、声音与附加展示 | 读取服务端事实；播放回调不结算伤害 |

配方、学习来源、内容版本、API 范围和所需能力使用稳定命名空间。目标可以引用组织能力，不把“右手”等人形部位写成通用运行条件。为某个具体身体实例配置时，再建立实际组织和端口映射。

## 后续动作配方示例

基础功法包可提供以下内容：

- 肌肉蓄力：消耗 n 元无属性真元，给对应肌肉 5 秒攻击增益。
- 真元拳击：另付真元和精力费用，攻击读取对应肌肉已生效的增益。
- 持剑挥击：要求实际使用手持有满足剑类能力、完好度和导元需求的武器。
- 轻步：作用于实际承担推进的腿部肌肉，多肌肉贡献由核心合成。

数值与动作公式由内容配置配合通用算子表达，仍须平衡。增益和攻击分别付费，异侧肌肉不能借用增益。不同附属包共享同一身体资源、控制任务位和增益叠加规则。

阅读功法授予配方或控制模板知识；客户端不能直接提交“已学会”。Fabric 和 Bong 的学习来源事件各由宿主验证，再进入同一解锁规则。单个附属包可含一组相关功法，不强制每个技能单独发布 JAR。

## 跨宿主内容

普通功法使用声明式定义。同一源内容构建为 Fabric 附属 JAR 和其他服务端内容包，由各服务端按相同规则版本解释。服务端实现语言不限；声明兼容的实现须通过对应行为验收。服务端由管理员安装定义，客户端只能请求调用，不能上传新定义改变服务端规则。

Java 书籍、界面或表现代码在 Fabric 执行；Bong 不直接执行 Java 字节码。新增核心没有的机制时，应提供共享运行能力，或交付明确支持的宿主适配并验证等价结果。缺必要能力就禁用对应配方并报告原因，不回退到另一套隐含规则。

扩展寿命时使用核心的寿命变更操作，保存实际发生的结果与来源。附属包被移除，不撤销已支付的寿元或已经完成的永久改造。

## 注册与权限

已实现加载流程：收集清单 → 检查依赖/API/宿主能力 → 校验定义归属、重复 ID 与类型引用 → 创建不可变注册表。宿主在启动期发布目录，再用模板初始化身体；新建身体的受控命令尚未实现。失败不能留下半套配方，详细合同见[附属包接入](Addon-Integration.md)。

运行时公开查询返回不可写快照；操作经核心与宿主的校验/事务提交。可信附属代码仍可以包含错误，因此官方和第三方内容使用同一校验路径；公共 API 不宣称能够沙箱隔离任意同进程恶意模组。

兼容和缺包规则见[兼容性](Compatibility.md)。
