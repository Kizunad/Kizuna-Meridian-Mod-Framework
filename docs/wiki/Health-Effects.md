# 伤害、治疗与主动疲劳恢复

状态：Protobuf 契约、可信宿主入口、独立 HP 变更、主动疲劳恢复、单次死亡保护、部位 HP 上限变更及内存原子事务已实现。原版战斗、治疗和物品副作用由宿主及独立附属接入；框架不提供人体伤害算法。

## 分工与唯一状态

部位、组织和器官各自持有 `hp`，通过 `HealthTarget` 的 `part_id`、`tissue_id` 或 `organ_id` 寻址。皮肤、肌肉、骨骼等是内容包声明的组织类型，各有独立定义与状态。对某组织治疗或扣血，不会自动修改所属部位及邻近组织；需要连带损伤时，由 Addon 明确返回多个目标。

经脉目前使用 `INTACT / LEAKING / SEVERED` 表达结构状态，没有新增经脉 HP。本次 HP 治疗不改变这些状态；断脉恢复、持续伤势与毒性周期另行实施。

| 参与方 | 职责 |
|---|---|
| 宿主 | 确认攻击、命中、治疗或药效事实，校验使用权限，按身体模板装配可信伤害处理器 |
| 伤害策略 | 框架兜底提供随机部位与直接扣血；生物 Addon 替换它，解释伤害类型、减伤、连带变化和是否致死 |
| Framework | 校验请求、目标与剂量，按固定结果改账，清理死亡资源，保存身体、环境释放及回执 |
| 客户端 | 展示权威状态；不能自报治疗量、恢复量或伤害处理结果 |

## 伤害接口

消息定义于 `shared/src/main/proto/kizuna/meridian/v1/health.proto`，Java 类型由 protoc 生成到 `HealthMessages`。流程为：

```text
可信 DamageBody → DamageContext（当前身体 + 伤害）
              → 默认处理器或 Addon 返回 DamageResolution
              → 框架校验并原子提交
```

`DamageBody` 包含来源 `source_id`、正数 `damage_hp`、可省略的命中 `hit`、具体类型 `damage_type` 和致伤机制 `kind = 5`。来源及具体类型为 `namespace:path`；来源用于追溯，不是授权凭证。省略 `hit` 表示交由策略选择；显式提供空目标、未知 ID 或非法分类仍会被拒绝。

可省略的 `death_protection = 6` 由可信宿主提供：`DeathProtection` 包含来源及 1–256 个唯一 HP 账户的正数下限，各下限不能超过账户实际上限。只有伤害策略将本次伤害判为致死时，框架才在同一事务中提高这些账户至指定下限并阻止死亡清账；非致死伤害也会校验完整方案。已经死亡的身体仍拒绝操作。保命物品是否存在、来源是否允许、下限能否满足该生物生存条件，由宿主和生物附属保证，框架不内置图腾或人体阈值。

### 致伤机制

`DamageKind` 枚举由 protoc 生成，编号固定；零值和未知编号拒绝。框架兜底对各类使用相同扣血规则，具体差异由生物 Addon 实现。

| 编号 / 枚举 | 含义与例子 |
|---|---|
| 1 / `BLUNT` | 钝击：拳击、碰撞、坠落、挤压 |
| 2 / `CUTTING` | 切割：剑刃、刀刃、割裂 |
| 3 / `PIERCING` | 穿刺：箭、矛、尖刺 |
| 4 / `HEAT` | 灼热：火焰、熔岩、高温 |
| 5 / `COLD` | 寒冷：冰霜、低温 |
| 6 / `ELECTRIC` | 电击：电流、雷电 |
| 7 / `CORROSIVE` | 腐蚀：酸液、接触性腐蚀物 |
| 8 / `TOXIC` | 毒性：已由宿主确认生效的毒性损伤 |
| 9 / `CUSTOM` | 附属自定义机制，具体含义由 `damage_type` 声明 |

五行、材料、武器和术式描述来源，不直接等于致伤机制。例如 `minecraft:fall` 使用 `BLUNT`；火焰主要使用 `HEAT`，火焰冲击也可由宿主拆为灼热与钝击。混合伤害的联合批次尚未定义，不能将多个独立请求声称为一次原子攻击。毒性分类只描述本次 HP 损失，不自动创建持续中毒。

### 通用随机部位兜底

`DefaultBodyDamageHandler` 是未显式装配策略时的默认实现：已有 `hit` 时只扣该账户；没有 `hit` 时，从实际 `part_states` 中 HP 大于零的部位等概率抽取一个。没有候选时返回 `MODULE_UNAVAILABLE`，不伪造部位。它不使用人体 ID、模型体积、护甲或五行分支。

默认策略只在投影结果中全部部位 HP 都为零时判死，不含头部、心脏等生物特定阈值。安装的 Addon 完整替换默认策略；它可以复用 `DefaultBodyDamageHandler.selectHit`，也可以自行决定未指定命中的选择规则。其他语言宿主实现相同等概率规则即可，不要求跨语言随机序列一致。

随机数只在新请求计算方案时抽取一次，具体受伤目标保存于 `DamageResolution.losses`。成功重试、存档恢复和 Store 复核沿用固定结果，不重新抽取；提交前失败没有固定命中承诺。Addon 拒绝或返回非法结果时，整次请求失败，不再尝试默认策略。

### 策略接口与固定结果

`DamageResolution.losses` 最多 64 项，每项是唯一目标与正数 HP 损失；空列表可表达免疫。`lethal` 必须显式设置，即使为 false。损失总和不强制等于输入，避免约束附属的减伤、穿透或连带模型。框架逐项验证目标确实存在，过量损失裁剪到零。某个部位归零也不会使框架自行改判死亡。

Java 参考装配接口为 `server.BodyDamageHandler.resolve(byte[])`：输入 `DamageContext`，输出 `DamageResolution`。`HealthProtobuf` 提供有界编解码。宿主将实现传入 `BodyCommandHandler` 的完整构造器，且可按模板路由到不同生物 Addon。省略该参数时使用上述默认策略；已装配的路由器仍可对缺少所需生物实现的情况返回 `DAMAGE_HANDLER_UNAVAILABLE`。其他语言使用同一消息与行为契约，无需加载 Java 类。

回调只计算方案，不写身体账本或发送世界副作用。一次新请求只调用一次；成功回执固定原始方案，事务复核不重新调用 Addon。已提交重试与存档重放也不依赖 Addon 当前版本。

## 治疗与主动恢复

`HealBody` 提供来源和 1–256 项唯一目标的 `Healing`。正数剂量恢复目标自身的 HP，止于实际构型的最大值。过量部分无效，不转给其他目标；死体拒绝，不支持复活。均分全身、溢出再分配及普通治疗排除零 HP 部位等规则，由治疗附属计算成明确剂量。

`SetPartHealthLimits` 提供来源及 1–256 个唯一部位的正数新上限。它调整实例实际构型，不修改模板；扩大上限不赠送 HP，降低上限将超额 HP 裁剪到新上限。附属负责记录自己的授予增量并在效果结束时撤销；来源字段不代表框架已实现通用属性叠加系统。

`RestoreFatigue` 提供来源和 1–32 项唯一目标的 `FatigueRelief`。目标为组织、声明独立耐力的器官或经脉，按自身单位减少疲劳，最低为零；器官单位为焦耳。体力或精力对应哪个组织，由生物内容定义，不另设平行账户。

主动恢复可以在动作占用期间生效，不停止动作；自然指数恢复仍遵守空闲条件。剂量须为有限正数，浮点舍入导致有效减量无法记录时返回 `NUMERIC_LIMIT`。治疗不会同时恢复疲劳，疲劳恢复不会同时治疗 HP。

## 可信入口与原子性

健康命令使用 `BodyCommandHandler.handleHealthEffect(context, payload)`，仍须经过身份授权、私有策略、身体版本及可信已结算活动时间检查。普通 `handle` 默认返回 `ACCESS_DENIED`，即使普通授权策略放行。宿主不得把可信入口直接注册成玩家可上传剂量的网络通道。

命令字段为 `BodyCommand.damage_body = 23`、`heal_body = 24`、`restore_fatigue = 25`、`confirm_body_death = 26`、`set_part_health_limits = 27`；回执为 `CommandReceipt.health = 11`。`HealthResult` 保存显式死亡标记、释放明细、仅伤害必填的固定处理方案及 `death_prevented = 4`。保命生效时固定原致死方案，但 `died = false`，避免先释放真元再伪造复活。非法目标、重复目标或任一失败均整批回滚；成功只增加一次身体 revision。成功去重键沿用可信调用者、身体和请求 ID。

`ConfirmBodyDeath` 仅携带可信来源 `source_id`，用于宿主已经确认的外部死亡。它不调用伤害策略、不伪造大额伤害，也不将局部 HP 归零；确认死态时保留伤势和疲劳，并按统一死亡规则释放资源。死体的新健康请求返回 `BODY_DEAD`，成功死亡请求的原身份重试仍返回旧回执，不重复释放。该操作没有复活语义。

Addon 判死后，框架清空动作与开脉任务，将内腔、外壁、在途、器官缓存及未完成加工输入各释放一次，保留属性与相态，预计产物不提前生成。非致死伤害使开脉所需模块失能时立即中断任务，撤销临时超压并释放超额。身体、释放账户和回执一起提交。

`InMemoryBodyStore.stage` 按固定方案复算身体与结果，拒绝被改写的候选；已有释放历史恢复时必须一起提供环境余额，不能重放释放。正式持久化实现须提供相同原子性，并与宿主实体死亡等可靠世界输出协调；审计回调只是提交后的尽力通知。

当前来源字段只提供效果追溯。物品扣除、材料费用、通用效果叠加与持续周期尚未合入健康操作；丹药或装备附属接入时仍需相应的可信使用与联合事务。部位上限变更也不等于通用属性修正系统。

## 跨附属健康宿主交换

`health_host.proto` 定义 `HealthHostRequest` / `HealthHostResponse`。Java 参考入口为 `server.BodyHealthHost.exchange(byte[])`，通过 `HealthHostProtobuf` 有界编解码；这是可信宿主与适配附属的装配边界，不可直接暴露为玩家网络通道。

请求包含协议版本 1、关联 ID、宿主身份 `subject_id`，以及 `inspect = true` 或健康 `RequestEnvelope effect`。外层和内层请求 ID 必须一致，内部命令仍带实际身体 ID 与预期 revision。宿主绑定身份、检查权限并按可信时刻结算；不能替调用方刷新预期 revision 来绕过并发校验。

响应为完整当前 `BodySnapshot`、`unbound = true` 或框架 `RequestFailure`。只有未绑定允许继续寻找其他宿主；拒绝、异常或多个宿主认领时不能切换账本执行。成功效果可附 `health = 13`，内容必须取自同一请求的固定 `HealthResult`；查询不附带，失败和未绑定响应禁止携带。成功重试可返回当前快照，但附带事实仍为原始成功回执。需要根据保命事实消费物品的调用方必须要求该字段，并用原命令核验结果，不能从当前 HP 猜测。其他语言宿主按同一 Protobuf 与行为契约提供入口即可。

## 伤害与临时效果集成

`BodyDamageIntegration.prepare(byte[])` 接收 `DamageIntegrationContext`：真实身份、当前身体、已固定命中的最终伤害以及保命绕过标记。返回 `DamageIntegrationPlan`，必须显式声明是否认领；认领方可减少剂量并提供保命方案，不能增伤或绕过来源禁用。同次伤害最多一方认领，多个认领明确拒绝。此阶段只读，不消费效果余额或物品。

剩余剂量大于零时，由原健康宿主提交身体；完全吸收则不生成零伤害事务。成功后调用 `committed(byte[])`，以 `DamageIntegrationCommit` 提供原上下文、方案、提交后身体和固定保命事实，集成方才扣除本次局部效果余额。通知不是崩溃恢复事务，不承诺外部副作用恰好一次。

Fabric 发现与原版伤害事件归独立 Vanilla Damage Addon，原版治疗和局部黄心归 Vanilla Healing Addon，Human 提供自己的身体宿主；Framework 不引入 Minecraft 或人体特例。游戏实体与身体账本的跨系统持久化协调仍由宿主负责。
