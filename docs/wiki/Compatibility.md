# 版本与兼容性

状态：尚未发布版本，当前不存在稳定公共 API、Maven 坐标或可安装 JAR。本页是首版发布必须满足的合同。

## 分别记录版本

- 各实现公开 API 的版本与兼容范围。
- 客户端/服务端线协议版本。
- 所选部署若使用原生桥接，其 ABI 版本及平台。
- 身体模板、功法定义和内容修订。
- 身体存档格式与必要迁移版本。

同一已发布 API 主版本内保持已有契约；新增扩展不静默增加调用方必须实现的方法。破坏性变化使用新主版本并给出迁移说明。预发布范围需要明确限定，不因数字相似就自动视为兼容。

服务端实现语言不限。实现相同 Protobuf 格式只证明数据能够交换；声明规则兼容还须通过同版本的单位、校验、失败语义及身体行为测试，不要求共享某一种语言的库或 ABI。

现有通信使用 `kizuna.meridian.v1` Protobuf 包，协议版本 `1` 与身体 schema `3` 分开验证。字段号和枚举数值不得复用，删除后须 `reserved`。当前编解码拒绝未知字段和未知枚举，新增字段不自动意味着旧端兼容；发布前需要配套版本协商与兼容矩阵。生成类型不提交源码，双方以同一版本 `.proto` 为准，Java 的类枚举顺序不构成线协议。

身体 schema 3 要求每条经脉显式提供 `MeridianState.opening = 6`，并由 `Qi.density = 4` 保存真元密度；容量字段按液态参照体积解释。schema 1/2 和缺少开拓数据的快照均拒绝，不按完好度、真元或境界补全。当前未提供旧开发快照迁移器；本轮不处理旧存档，两端须同步使用当前协议产物。

当前开发版用 `TissueDefinition.recovery_half_life_seconds = 10` 替代线性恢复，旧字段 `rest_recovery_per_second = 9` 及 `TimeAdvancePlan.resting_tissue_ids = 4` 的编号和名称均 reserved。带旧字段的消息不自动迁移；没有旧字段的新建数据以半衰期零表示禁用恢复。宿主须同步支持 `meridian:tissue_recovery_v2` 和按 `BodySnapshot.actions = 14` 判断占用；不能继续声明 v1 后套用新公式。动作定义通过 `meridian:actions_v1` 登记。当前仍保持开发中的协议 1、schema 3，发布前须冻结版本并提供正式迁移策略。

环境配置版本 2 新增业务必填 `generation = 7`；版本 1 和缺少生成配置的完整消息均拒绝。TOML 覆盖文件省略版本时沿用当前默认值，显式写 `config_version = 1` 的旧开发配置须改为 2 并检查新默认地形表。线协议版本 1、生成算法版本 1、宿主规则世代各自独立；新生成规则不能重新初始化已有区域余额。

## 附属包清单

当前开发版增加 `AddonBundle.opening_rules = 7` 与内容种类 `MERIDIAN_OPENING_RULE = 4`。旧端仍会按严格未知字段/枚举检查拒绝含新内容的包；两端须使用同一版本协议产物。未提供开拓内容的现有包可以继续登记，身体 schema 不因此变化。`meridian:opening_definitions_v1` 只声明定义支持，不能用于声称已支持开拓运行。

已实现 `AddonBundle` 清单与 `AddonRegistry`：每包声明独立命名空间、内容版本、API 范围、定义 schema、直接依赖、必要运行能力和支持宿主。重复定义、循环依赖、缺必要能力或不兼容版本在启用前拒绝整个候选批次，加载顺序不能决定覆盖结果。字段与诊断见[附属包接入](Addon-Integration.md)。客户端资源要求和资源校验仍待实现。

普通配方定义可以同时供 Fabric 与 Bong 核心解释。Java 自定义玩法回调不自动具有 Bong 兼容性；需要配套运行能力或宿主实现。现有八仓按适用端整套安装，不能以缺包回退替代必需接线；必需交互或模型资源缺失时明确报错。

服务端控制允许内容和实际知识，客户端安装的包不授予权限。服务器资源包分发资源，不自动安装可执行 JAR。

## 存档与缺包

稳定身份使用命名空间 ID 和实例 ID，不把数组位置或 Java 类名当存档键。正在运行的动作固定内容修订，首版在停止相关运行后切换定义，不中途改变成本或效果。

功法包缺失时保留知识、熟练记录和蓝图，将引用标为不可用。身体改造、已支出的寿元和实际真元不随包移除重置。无法按已保存规则恢复或终止的状态，阻止激活相关身体并提示恢复依赖或显式迁移；不能静默删档。

人体包与其他生物包遵循同一内容依赖规则。`findTemplate` 在精确模板缺失时返回空，宿主不能新建该模板的身体，也不能由主框架补一个默认人体。已有快照按实际构型和保存状态恢复，不重新套用出生数值。已启动固定配方可以按内嵌参数继续；活动开脉另依赖原策略执行器，缺失时安全暂停并解除动作占用，保留合法库存和稳定体积，不妨碍只读恢复快照。

开发中的开脉条件已迁往附属 Protobuf：原规则字段 `5、7、8、11、12、14、19` 的编号与名称 reserved，新增 `policy_id = 22 / policy_config = 23`。旧开脉规则和含旧规则的任务不会自动迁移，需要同步重建内容；本轮没有旧开发存档迁移器。`BodyViewUpdate.operations = 5`、默认展示层与玩家皮肤字段也要求两端同步更新协议产物。

`ContentReferences` 和 `ContentAvailabilityReport` 已提供包缺失、定义缺失、版本缺失与可用四种状态，保留每个精确引用及顺序，不自动升级版本、不删除存档。恢复同一包与修订后重新查询即可变为可用。知识、熟练度、蓝图及它们的实际持久化尚未实现，此诊断入口供后续复用。

3D 经脉世界作为纯交互 Addon 时，移除它只失去 3D 操作入口与展示能力；核心持有的身体、有效逻辑线路和执行进度应能通过基础操作入口继续使用。显示布局可保留为附属展示数据。若另有配方或运行能力依赖同时缺失，按对应内容依赖处理，不因 3D 画面缺失改写余额或停止身体。这是后续客户端与逻辑线路实现的验收要求。

器官单批次加工在存档内固定完整 `OrganRecipe` 与输入归属，卸载包后仍能按原规则完成；新请求需目录存在精确 ID/版本。已保存的成功回执重试也不重新查包。目录可用性不等于角色已学会配方，执行仍经过宿主授权与私有策略。

首版增删 JAR 需重启。模板/配方数据的重载、旧版本迁移和对外兼容矩阵必须有实际测试与发布说明，未验证前不承诺热加载。

不要求兼容重构前的旧 Bong 功法存档；这与新公共框架对已发布扩展的兼容承诺不同。
