# 架构与职责

状态：产品边界已确认；[基础数据类型与结构校验](Data-Definitions.md)、[Protobuf 数据交换与参考查询处理器](Protocol-and-Security.md)已实现，身体运行模块、变更操作接口和实际宿主传输适配尚未实现。

## 依赖方向

```text
功法附属 JAR / 服务端内容包
             ↓ 公开 API 与声明式定义
经脉基础模组：身体、寿命、经脉、通用操作、编辑器
             ↓ Protobuf 请求与响应契约
权威身体服务端（Java / Rust / 其他实现语言）
             ↓ 宿主适配
Fabric 内置或专用服务端 / Bong / 其他宿主
             ↓
真实世界、实体、物品、环境账户与存储
```

上图表示运行接入关系，不指定核心的实现语言或部署进程。任何满足通信和行为契约的核心均可提供服务端实现，宿主提供可信上下文并消费结果。每具身体只由一个权威执行方结算，不要求不同宿主链接同一份二进制库。

| 模块 | 拥有的职责 |
|---|---|
| 部位 anatomy | 构型、部位层级、结构连接与几何映射 |
| 组织 tissue | 单块肌肉、皮肤、器官及其功能、疲劳与损伤 |
| 经脉 meridian | 经脉模块、端口、实际连接、内腔与外壁状态 |
| 生命 vitality | 年龄、寿命、寿元损耗/增益与生命状态 |
| 身体核心 | 唯一实例状态、能力派生、真元运行、通用配方操作与成长 |
| 内景 workshop | 镜头、3D 场景、铺带、器官配方、草稿与运行诊断 |
| 功法扩展 | 具体功法、配方参数、路线模板、学习来源和专属表现 |
| 宿主适配 | 身份、时间、装备/知识事实、世界事务、存储与私有安全策略 |

一个经脉实例为最小改造模块。部位可以包含多块肌肉和器官；经脉通过端口服务组织，不把器官物理位置解释成“长在经脉内腔”。模板定义与角色实例分开，修改一个角色不能影响所有同种生物。

## 基础模组保持独立

- 基础模组只认识注册的数据与能力，不按具体功法 ID 写分支。
- 核心拥有通用增益和配方执行机制，附属包决定哪些配方消耗多少真元、产生什么效果。
- 基础模组单独可启动，基础生命不依赖真元或特定功法。身体的本能养护不占据唯一主动任务位。
- 默认可玩内容由官方基础功法附属包提供，使用与第三方相同的接口。
- Inventory UI Framework 提供公共窗口设施；经脉模组负责身体内容与 3D 内景，不反向依赖 Bong 私有界面类。
- 植物、炼丹、装备等模块通过宿主提供的受控接口影响身体，不能直接写身体的私有状态。

## 数据与执行

框架不仅渲染经脉，也定义、管理并保存身体状态。客户端快照是只读投影，服务端身体实例是权威状态；世界数据库由宿主适配，不能因此再产生一份可独立变化的寿命或真元余额。

跨模组与宿主边界以 `.proto` 为通信定义的唯一来源，protoc 生成 Java 消息及共享描述集。`core` 保留不依赖 Protobuf 的不可变模型和校验；`protocol` 负责生成类型与核心值之间的转换。器官、组织与经脉在协议中同样各自独立，通过部位和端口引用连接。生成消息不是权威状态，也不自带身份权限。

现有 Java 数据类型是参考实现，不是其他服务端必须链接的运行库。其他语言从同一契约生成消息，在自己的核心中完成校验和执行；同版本规则的实现须通过共同的输入输出、守恒、时序和失败无副作用验收。Protobuf 统一数据交换，不能自动保证各实现的计算结果一致。

当前 `server.BodyQueryHandler<C>` 实现只读查询边界：有界解码 → 宿主读取权限策略 → 权威快照来源 → 校验目标身份 → 编码响应。可信上下文由宿主提供，处理器不维护第二份身体，也不推进时间或资源；实际网络与身体变更执行器另行接入。

身体能力只在相关状态变化时重算。运输到达、来源耗尽、目标填满、配方完成、增益到期和寿命边界由事件推进；无界零时间循环应被拒绝。客户端动画不参与结算。

具体数据与保存边界见[身体与持久化](Body-and-Persistence.md)。
