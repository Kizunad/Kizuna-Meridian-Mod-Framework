# 架构与职责

状态：产品边界已确认；[基础数据](Data-Definitions.md)、[Protobuf 查询与变更](Protocol-and-Security.md)、寿命、运输、组织能力/做功、器官配方、宿主事务/策略及环境释放的内存参考已实现。连续流、肌肉真元增益/攻击、实际宿主调度/实体死亡、网络与正式持久化仍待实现。

## 仓库布局

沿用 Kizuna-Backpack-Storage 的两端目录与共用协议布局：

```text
client/                 客户端 Gradle 子项目
server/                 服务端 Gradle 子项目
  src/main/java/        身体模型、计算、协议校验与宿主处理器
  src/test/java/        服务端整体回归测试
shared/src/main/proto/  两端共用的 Protobuf 定义
docs/wiki/              文档源
```

`client` 与 `server` 分别构建 Java 库 JAR，根工程统一运行构建和检查。`shared/` 是协议源目录，不是第三个 Gradle 子项目；两端从同一份 `.proto` 独立生成消息，客户端无需依赖服务端实现。

目前 `client/` 只提供生成的协议消息类，基础操作界面和客户端网络接入尚待实现。3D 经脉世界规划为可选独立 Addon，其场景、镜头与建造交互归附属模组。现有身体模型、纯计算、编解码校验、处理器及整体测试均位于 `server/`，Java 包名保持不变。两端当前均为普通 Java 库；Fabric 加载入口、网络注册、实体生命周期和存档适配仍是后续工作。

## 依赖方向

```text
基础简易操作界面 / 生物附属包（含人体） / 功法附属包 / 可选 3D 经脉世界 Addon
             ↓ 公开 Protobuf 契约：查询、操作意图或内容定义
经脉基础框架：身体、寿命、经脉、真元引导与通用操作
             ↓ Protobuf 请求与响应契约
权威身体服务端（Java / Rust / 其他实现语言）
             ↓ 宿主适配
Fabric 内置或专用服务端 / Bong / 其他宿主
             ↓
真实世界、实体、物品、环境账户与存储
```

上图表示运行接入关系，不指定核心的实现语言或部署进程。任何满足通信和行为契约的核心均可提供服务端实现，宿主提供可信上下文并消费结果。每具身体只由一个权威执行方结算，不要求不同宿主链接同一份二进制库。

| 模块 | 拥有的职责 |
|---|---|
| 部位 anatomy | 构型、部位层级、结构连接与几何映射 |
| 组织 tissue | 单块肌肉、皮肤等组织的力量/功率/耐力、疲劳与损伤 |
| 器官 organ | 自身 HP、端口缓存、输入加工输出及配方执行事实 |
| 经脉 meridian | 经脉模块、端口、实际连接、内腔与外壁状态 |
| 生命 vitality | 年龄、寿命、寿元损耗/增益与生命状态 |
| 身体核心 | 唯一实例状态、能力派生、真元运行、通用配方操作与成长 |
| 生物附属包（含独立人体模组） | 具体生物构型、基础数值、初始寿命、器官固有摄入/加工配置及生命条件 |
| 基础操作客户端 | 来源/目标选择、配方参数、路线预览及运行诊断展示 |
| 可选 3D 经脉世界 Addon | 镜头、3D 场景、铺带、多方块交互与布局草稿；把编辑结果转换成公开操作意图 |
| 功法扩展 | 具体功法、配方参数、路线模板、学习来源和专属表现 |
| 宿主适配 | 身份、时间、装备/知识事实、世界事务、存储与私有安全策略 |

一个经脉实例为最小改造模块。部位可以包含多块肌肉和器官；经脉通过端口服务组织，不把器官物理位置解释成“长在经脉内腔”。模板定义与角色实例分开，修改一个角色不能影响所有同种生物。

## 人体作为独立附属模组

已确认：人体内容由独立附属模组维护和发布，主框架不内置人体模板或人体专属分支。人体部位、肌肉、器官、经脉及连接图，基础 HP/力量/寿命，肺的摄入与炼化配置，关键部位及死亡条件都由人体包提供。其他生物包采用相同公开契约，官方人体包没有特殊入口。人体包的实现与发布尚未开始。

主框架提供可组合的身体类型、能力契约和通用算子，按已验证定义计算；附属包通过 Protobuf 提交内容和意图。人体包决定“肺采用哪些输入、效率及产物”，主框架执行“指定器官按已声明能力摄入、加工与转运”。通用摄入与环境/身体原子交换已实现；人体包后续配置肺与首脉起步，可改造的按属性炼化效率和伤害死亡条件仍需补齐通用契约。

内容归属与状态归属分开：人体包提供初始定义，实际构型、器官改造结果、年龄、寿命和真元仍由权威核心保存。功法包提供学习获得的配方与运行模板；人体固有生理能力属于人体包，不要求先学习功法。基础模组可以独立加载，但不会自动创建默认人体；宿主根据已安装、已验证的生物内容创建身体。缺失内容时保留实际状态，按[缺包规则](Compatibility.md)处理。

## 基础模组保持独立

- 基础模组只认识注册的数据与能力，不按人体、器官名称或具体功法 ID 写分支。
- 核心拥有通用增益和配方执行机制，附属包决定哪些配方消耗多少真元、产生什么效果。
- 基础模组单独可启动，基础生命不依赖真元或特定功法。身体的本能养护不占据唯一主动任务位。
- 默认人体内容与基础功法分别由官方人体附属包、官方基础功法附属包提供，使用与第三方相同的接口。
- 不安装 3D Addon 也应能通过基础操作入口引导真元和使用已学配方。功法包提供内容，3D Addon 提供另一种操作方式，两者可独立选择。
- Inventory UI Framework 提供公共窗口设施；基础操作面板与 3D Addon 可分别接入，不反向依赖 Bong 私有界面类。
- 植物、炼丹、装备等模块通过宿主提供的受控接口影响身体，不能直接写身体的私有状态。

简易操作与 3D 铺带共用同一逻辑线路和执行规则。界面可辅助选择路线，实际连接、开拓状态、吞吐、容量、精力、控制延迟和配方条件仍由权威核心校验。3D 坐标只组织画面，不决定真实连通性或额外资源。Addon 所需的编辑会话与受伤退出由宿主适配配合校验；运行无需加载其场景。具体交互建议见[经脉操作与 3D Addon](Inner-World.md)。

## 数据与执行

框架定义、管理并保存身体状态，操作端负责展示和提交意图。客户端快照是只读投影，服务端身体实例是权威状态；世界数据库由宿主适配，不能因此再产生一份可独立变化的寿命或真元余额。

跨模组与宿主边界以 `.proto` 为通信定义的唯一来源，protoc 生成 Java 消息及共享描述集。`core` 保留不依赖 Protobuf 的不可变模型和校验；`protocol` 负责生成类型与核心值之间的转换。器官、组织与经脉在协议中同样各自独立，通过部位和端口引用连接。生成消息不是权威状态，也不自带身份权限。

Java 运行时的异常类型和错误文案集中在 `error.MeridianErrors`；摄入和附属包拒绝直接携带 protoc 的失败码或诊断消息。校验条件、业务顺序和异常处理保留在各层，公开失败码继续由 Protobuf 定义，详见[请求协议与安全扩展](Protocol-and-Security.md)。

现有 Java 数据类型是参考实现，不是其他服务端必须链接的运行库。其他语言从同一契约生成消息，在自己的核心中完成校验和执行；同版本规则的实现须通过共同的输入输出、守恒、时序和失败无副作用验收。Protobuf 统一数据交换，不能自动保证各实现的计算结果一致。

`server.BodyQueryHandler<C>` 提供完整身体与组织能力查询；`BodyCommandHandler<C>` 提供受授权的寿元支出、时间结算、运输、加工启动、组织做功和环境摄入，以及版本、去重、私有策略和原子提交。`core` 的纯算子负责计算，`BodyResourceEvents` 按时间合并到达与加工完成，`BodyTimeSource` 提供可信时间，`BodyEnvironmentSource` 确认摄入区间的可信来源。`OrganRecipeCatalog` 只安装经过验证的 protoc 配方定义，不依赖具体功法包。`BodyTransactionStore` 负责身体、来源库存、共享预算和回执一起提交；`InMemoryBodyStore` 是无磁盘参考。处理器不另持一份身体，也不在审计通知里执行世界副作用。

身体能力只在相关状态变化时重算。运输到达、来源耗尽、目标填满、配方完成、增益到期和寿命边界由事件推进；无界零时间循环应被拒绝。客户端动画不参与结算。

`server.AddonRegistry` 已接收完整 Protobuf 附属包候选，检查依赖、兼容范围、能力和类型引用后生成不可变目录。模板用于宿主新建身体，配方目录接入现有命令处理器；已保存身体与正在加工的固定配方不随包卸载而重置。通用内容接入与缺包报告见[附属包接入](Addon-Integration.md)。

具体数据与保存边界见[身体与持久化](Body-and-Persistence.md)。
